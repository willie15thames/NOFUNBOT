# Template, naming and fallback audit — RC4

Reviewed 27 September 2026. The code scan covers the 194 JavaScript files in `index.js`, `src/` and `scripts/`, with focused traces through setup, edit, rules presets, nickname enforcement, channel resolution, active checks and diagnostics. Counts in the final RC4 source are lexical review candidates, not a count of bugs: 473 `.catch(() => null)` occurrences in 49 files, 168 empty `catch` blocks in 45 files, 36 single-line channel-cache lookups referencing `.name` in 16 files, and 104 `.delete(` occurrences in 35 files. A `.delete(` match may be a Map removal rather than a Discord deletion. Multi-line name lookups and alternative catch styles are outside those simple counts. Review each call site with its caller, expected permissions, persistence boundary and idempotency contract before changing it. A blanket removal of catches would break optional functionality and rate-limited Discord paths.

Concentration matters: `interactionRouter.js` contains 196 null catches and 54 empty catches; `index.js` contains 50 and 23; `hubScreenshotParser.js` contains 35 null catches; `flowDefinitions.js` contains 10 and 19; `patchNotesService.js` contains 25 and 3. These are triage starting points, not findings that every catch is wrong. The router alone accounts for a large share of optional response and best-effort interaction handling, so it needs action-by-action review before altering error semantics.

## Confirmed failure clusters addressed in RC4

1. League text channels no longer repeat the league prefix. The unique category and resource IDs identify the league. Readers also recognize legacy dotted and concatenated two-character channel names, so an existing league need not be rebuilt to use a rules preset or active check. Two leagues may have the same first two letters.
2. Rules preset lookup stays within the selected league's recorded categories and channels. It no longer mistakes the server's `#rules` or another league's `#rules` for its own. A missing channel produces an actionable response. Replacement posts before old matching bot posts are removed, retaining the last published rules if a send fails.
3. Discord nicknames are guild-wide. Channel activity cannot oscillate a member between two league team names. A single team assignment may be shown; multiple active assignments use the member's saved base name, with timezone retained. The duplicate hierarchy listener and message-driven base-name rewrite were removed.
4. A template edit builds the new selection before cleanup. It deletes obsolete channels only when their bot-generated topic, name and parent still match captured evidence. An empty old category is then deleted; manual children, renamed or retopiced channels, private league assets and protected channels remain. The build manifest is stored for future edits. Missing new assets abort cleanup.
5. Channels with the same name in different categories are no longer adopted or moved globally. Base channel resolution prefers the intended base/staff category and excludes known league channels.
6. Active-check creation fails closed when the selected league lacks a private category or member role. It searches only that league's categories and sets private overwrites. The league resource ID registry is updated after creation.
7. Base permission normalization skips registered league channels; otherwise a league's plain `#rules` could have inherited a base channel's public overwrite. A rejected permission edit now reaches the build caller.
8. Base guide replacement posts the new content before deleting the previous bot post and reports a failed send. Core guide and permission errors propagate through the final build steps instead of yielding false success. Noncritical positioning and patch-note attempts still have their existing best-effort semantics.
9. Channel diagnostics distinguish the seven core base channels from the full optional catalog. Database wording reports a failed schema probe rather than claiming the schema was never deployed. The Railway example now defaults migration and bootstrap boot flags off, documents the persistent data mount, and identifies RC4.

## Remaining risk register and follow-up work

| Priority | Area | Evidence and consequence | Needed change or acceptance check |
| --- | --- | --- | --- |
| High | Full initialization/reset | `flushServerChannels` considers most cached guild channels deletable, while its failures are only returned in a summary. This is broader than the guarded template edit path. | Inventory exact owned IDs and obtain an explicit commissioner preview before any full reset. Abort on deletion failures. Verify manual and other league resources survive in staging. |
| High | Legacy privacy | An existing legacy channel may have manual or inherited overwrites that differ from newly built private spaces. | Reconcile effective access for every legacy category and child with real Discord member accounts; do not infer privacy from a role ID alone. |
| High | Partial remote operations | Discord create can succeed and the following state write can fail. Active-check or template assets can then exist without a complete durable registry entry. | Use a durable operation journal with exact Discord IDs and a repair command; verify replay after crashes and permission failures. |
| High | JSON compatibility and concurrency | `templateBuildManifest.json` and several legacy stores still use compatibility JSON. Database critical keys protect selected state, but local projections and one-writer assumptions remain. | Migrate ownership metadata and legacy projections to PostgreSQL, test restart and rollback with a mounted volume, and retain one bot replica until the write paths are transactionally isolated. |
| Medium | Manual edits to old template assets | Renaming, moving or retopicing an old bot channel destroys reliable ownership evidence; automatic deletion intentionally preserves it. | Provide a preview of unmatched suspected assets, explicit ID-based commissioner cleanup, and a record of what was retained. |
| Medium | Remaining broad lookups | The final scan found 36 single-line channel-cache lookups referencing names in 16 files; only the traced setup, rules, base and active-check paths were corrected here. | Classify each by base, league, event or global scope; replace ambiguous lookups with recorded IDs and focused tests. |
| Medium | Suppressed failures | 473 null-catching expressions and 168 empty catch blocks are review candidates; many guard optional functionality. Their count does not establish 641 defects. | Triage by destructive action, privacy, core write, optional output; make failed core actions visible and add a repair state where remote side effects may already exist. |
| Medium | Nickname policy | The chosen stable guild display prioritizes a single team or saved base name. Permission or role hierarchy can still block changing a nickname. | Show an actionable failure and test members with multiple leagues, role changes, timezone changes and reconnects in staging. |
| Medium | Category identity | Template matching still uses category names to find desired categories, and identical manually created category names can be ambiguous. | Record category IDs in the manifest and resolve by ID on subsequent edits; require explicit user choice for collisions. |
| Medium | Diagnostics | Seven core channel checks are useful but do not prove every selected template or league workflow has the channels and permissions it needs. | Add per-template and per-space readiness checks against recorded IDs and effective permissions. |

## Verification boundary

Focused tests cover rules isolation and send failure, nickname stability, old-channel cleanup with manual preservation, empty-category removal, duplicate names across categories, duplicate league prefixes, private active checks, base permission isolation and failure propagation. Run the full local suite and TypeScript check before upload. Discord API permissions, existing live channel layout, Railway volume ownership, migration state, real PostgreSQL and backup restore require staging verification. This release is source code only; it does not erase or migrate any live channel during packaging.
