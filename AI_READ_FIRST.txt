NOFUNLEAGUE ENGINEERING AI ACCOUNTABILITY DIRECTIVE v2

PURPOSE
This file governs any AI or developer modifying, refactoring, or repackaging the NOFUNLEAGUE codebase. The ZIP/source provided in the current session is the source of truth for the current implementation.

PHASE 1 - BEFORE EDITING
1. Read this entire file.
2. Read PATCH_NOTES_AND_CONTEXT.txt and identify the recent changes that touch the requested area.
3. Read CODEBASE_NAVIGATION.md and DEDUP_ARCHITECTURE.md.
4. Extract and inspect the current source tree. Never rely on remembered prior sessions.
5. Identify every file that will change.
6. For every changed export/function, find callers before editing the signature.
7. Identify current state owners before adding new state.
8. Identify whether the requested feature already has a partial implementation.
9. Write a short dependency map before modifying shared services.

PHASE 2 - NO-REGRESSION RULES
10. Preserve existing behavior unless the requested change explicitly changes it.
11. Never delete a path because it looks duplicated until all callers and tests are mapped.
12. Prefer adapter/compatibility wrappers over simultaneous signature changes.
13. Do not flush or delete server structure in edit mode.
14. Use find-or-create functions for structural Discord resources.
15. Use the central message-send service where required by the current architecture.
16. Do not create a new dedup layer. Extend the documented layer only when necessary and update DEDUP_ARCHITECTURE.md.
17. Any new Map used for dedup/cooldown must have TTL cleanup or a max-size policy.
18. Any new process timer must have explicit lifecycle management; no timer may be the sole authority for durable league state.
19. No new critical loop may depend on process memory surviving a deployment/restart.
20. Do not silently swallow critical errors. Optional cosmetic work may fail safely, but the result must remain observable.

PHASE 3 - LEAGUE AUTOMATION RULES
21. Never treat a timer expiry as proof that Madden advanced.
22. Workflow week and source week are separate values.
23. A new week is publishable only after source advancement is verified and required import validation passes.
24. Use a league-specific distributed lock for advance/import/publish cycles.
25. Use idempotency keys for provider control, webhook delivery and import processing.
26. Provider capabilities are explicit. Unsupported capabilities must return a structured unsupported result.
27. Discord publication occurs after durable database commit.
28. Manual import remains an emergency fallback until direct providers are proven stable.

PHASE 4 - AI RULES
29. AI output must use a registered action catalog.
30. Never add action types to a prompt without adding the matching executor/schema/test.
31. Destructive actions require application-enforced confirmation.
32. AI may not invent data, provider capabilities, completed actions, permissions or system state.
33. Do not use self-reported AI confidence as a security control.
34. Do not require or store hidden chain-of-thought. Store concise audit reasons/decision metadata only when explicitly defined by the schema.
35. Runtime AI prompts must not contain secrets.
36. AI-generated predictions are analysis, never authoritative league state.

PHASE 5 - VERIFICATION
37. Run node -c on every modified JS file.
38. Run the TypeScript/config validation commands that apply to the changed surface.
39. Run targeted tests for the changed flow.
40. Run regression tests for setup, edit mode, AI mention routing, team assignment, game channel lifecycle, trade flow, stream flow and startup recovery.
41. For provider work, test duplicate webhook, delayed webhook, malformed data, missing team, wrong week, partial import, provider 429/5xx, and restart recovery.
42. Verify all new files are included in the release package.
43. Verify the release package has index.js at its root when the deployment expects a flat package.
44. Update patch notes with version/date/affected files/fix/risk/test evidence.
45. Do not claim verification that was not actually performed.

PHASE 6 - RELEASE GATE
46. If any P0/P1 regression remains, do not release the feature to production.
47. If a provider control path is unverified, expose the capability as unsupported/assisted, never as automatic.
48. Keep compatibility flags until the new path passes the trial run.
49. Preserve rollback by retaining the previous provider/path behind a feature flag until cutover is complete.
50. A release is complete only when code, state migration, documentation, tests and operational recovery are all aligned.

V203.1 STABILIZATION ADDENDUM - REQUIRED
51. User decision superseding v18: ordinary channel names inside unique league categories are authoritative. Preserve legacy prefixed discovery through leagueNamingService; never broadly rename or delete existing channels. Native nicknames remain stable per guild; per-league labels belong in bot output.
52. leagueChannelName() and leaguePrefixCode() are owned by src/services/leagueNamingService.js. Do not duplicate inline naming logic in setup/feature services.
53. A PrismaClient object existing does not mean PostgreSQL is healthy. Operational checks must use probePrisma()/getPrismaHealth() and distinguish clientInitialized, reachable, and schemaReady.
54. Production Railway configuration must not use localhost for separate PostgreSQL/Redis services. Deployment validation must reject known placeholder credentials/secrets before boot.
55. The advance engine is the deadline authority once an explicit automation policy exists. Do not introduce a second recurring 48-hour timer in a Discord presentation service.
56. Router-only command cases must be classified in docs/COMMAND_HANDLER_MANIFEST.md and scripts/command-contract-check.js. Public command visibility must not silently regress.
57. Before packaging, run the unresolved-identifier guard. node --check only proves syntax and cannot detect missing runtime identifiers.
58. Legacy JSON, PostgreSQL and Redis must never be treated as equal business-state authorities. Follow data/JSON_OWNERSHIP_MAP.md and document any cutover before changing read authority.
59. Dedicated queue-worker readiness requires both Redis and PostgreSQL. Do not restore an unref'd retry loop that claims to keep the process alive.
60. Do not convert broad best-effort catch behavior in one sweep. Replace silent catches only where the operation is classified, tested, and the caller can handle the new error/result contract.
V204.7 CONVERSATION INTELLIGENCE ADDENDUM - REQUIRED
61. Passive conversation awareness may observe permitted human guild messages only into bounded, short-lived, channel-local memory. Observation must not itself call AI, type, react, reply, mutate state, or persist message bodies.
62. Conversational AI speech requires an explicit bot @mention. Channel location or reply-to-bot alone is not speech authorization. Slash commands, components, moderation, scheduled automation, and provider/system events remain separate explicit event paths.
63. Ambient conversation text is untrusted context only. Never execute or authorize an action from ambient context, and never let it override permissions, action-catalog schemas, confirmation policy, or domain validation.
64. Natural-language planners are adapters into existing domain services, not new state owners. Resolve intent and entities, ask only for genuine ambiguity, and call the same service used by the slash command.
65. Multiple leagues are not automatically ambiguous. Ask for league scope only when the requested entity has multiple valid league-scoped matches or the existing domain owner requires an explicit scope.
66. Pending conversational clarifications must be bounded by user+guild+channel, expire quickly, and revalidate live state before mutation. Pending context is never a reservation or lock.
67. Do not persist passive chat history by default. Any future persistence requires an explicit privacy/retention design and migration review.
68. Regression tests must prove: unmentioned messages cause no AI speech; no cross-channel ambient leakage; ambiguous member/team/league cases fail safe; and unique natural assignment reuses the existing assignment domain path.


V204.7 RELEASE-CLOSURE ADDENDUM - REQUIRED
69. Server structure has exactly three public modes: base, template, custom. Base has no selected template/subtemplate and MUST NOT silently default to gaming or any other family. Template uses one family plus its relevant built-in subtemplate. Custom composes commissioner-selected families/subtemplates with deterministic deduplication.
70. The legacy Empty structure option is retired. Treat migrated legacy empty/base intent as Base, not as a hidden template.
71. Natural-language planning should be broadened only where an existing domain owner/action can safely receive the resolved request. The planner resolves intent/entities; it does not duplicate persistence or bypass permission/confirmation rules.
72. Fresh natural requests MUST NOT inherit stale pending entities. Pending clarification state may fill only the missing field(s) of a genuine continuation and must be revalidated immediately before mutation.
73. Provider push endpoints MUST NOT return a success acknowledgement until the receipt and required raw artifact are durable under the production authority. Background processing is recovery/execution, not acknowledgement durability.
74. Provider connection authority is league-scoped. A production league must not have multiple competing active external providers; ambiguous authority fails safe to local/manual behavior.
75. Provider secrets are encrypted at rest and never echoed after initial route/token issuance. Receiver tokens are capabilities and must be hashed/stored/redacted accordingly.
76. Direct EA remains disabled/unsupported until a legitimate authorized Madden interface exists. Do not implement password collection, cookie/session replay, or private control endpoint scraping.
77. Before production promotion, the clean-install full suite, TypeScript validation, Prisma migration validation, release verifier and deployment preflight must all pass. A package may be called a production candidate before these gates, but not production-certified.
